# 版本号维护与递增规范 (Version Bump Rule)

## 核心原则
为了保证应用打包、发布及版本追溯的清晰性，杜绝打包时重复使用旧版本号，AI 必须严格遵守以下版本管理行为准则：

## 触发时机
每当完成一次代码修改（无论是新特性开发、缺陷修复、UI优化还是配置调整）并通过本地测试验证后，在向用户交付结果时，**必须主动向用户发起版本号递增询问**。

## 交互与执行流程

1. **主动询问**：
   - 明确指出当前项目的全局版本号（来自 `package.json` 的 `version`）；
   - 给出推荐递增的补丁版本号（Patch Version，例如 `1.4.0` -> `1.4.1`，特殊重大重构或新功能可建议 Minor Version，如 `1.5.0`）；
   - 询问格式示例：
     > “本次代码修改已完成并通过测试，当前版本号为 **1.4.0**。请问是否需要将全局打包版本号递增至 **1.4.1**？”

2. **用户确认后的执行动作**：
   若用户确认递增版本号：
   - **更新 `package.json`**：将 `"version"` 字段修改为新版本号；
   - **更新 `package-lock.json`**：同步根节点 `"version"` 及 `packages[""].version`；
   - **更新 `CHANGELOG.md`**：在文件顶部第一条位置插入该版本的日志模块，格式保持标准模板（包含版本号、发布日期、分类要点）；
   - **生成运行时版本元数据**：运行 `npm run version:gen`，刷新 `src/renderer/src/generated/version_info.json` 与 `version_info.ts`；
   - **向用户汇报更新结果**：确认版本号已递增，新版本将在下一次打包（`npm run release:sync` 或本地 Electron 编译）时生效。

3. **用户否定或未确认时的执行动作**：
   若用户明确表示不需要更新版本号、或未确认更新：
   - 严格沿用当前版本号，不修改任何版本配置文件；
   - 仅对修改的业务代码和测试用例进行提交或保持就绪状态。
